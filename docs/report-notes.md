# 보고서에 쓸 설명 포인트 모음

테스트하면서 나온 "헷갈리기 쉬운 차이"와 "설계 이유"를 모아 둔 메모입니다. 보고서에는 이 문장을 그대로 옮기지 말고, 코드와 증거를 직접 확인한 뒤 **자기 말로** 다시 쓰세요. 각 항목의 근거 증거와 코드 위치를 함께 적어 두었습니다.

## 1. 인증과 권한의 구분

### 1-1. 401과 403은 다르다
- **401**: 요청한 사람이 누구인지 확인하지 못함(인증 실패). 토큰이 없음·변조됨·만료됨 → 다시 로그인해야 함
- **403**: 누구인지는 확인했지만 그 일을 할 권한이 없음(권한 부족). 토큰은 멀쩡함 → 로그아웃시킬 이유가 없음
- 그래서 프론트도 다르게 처리함: 401이면 메모리의 토큰·사용자를 지우고 로그인 화면으로, 403이면 로그인 상태를 유지한 채 안내만 표시
- 코드: `frontend/src/api.js`의 `request()` (`response.status === 401`일 때만 `clearSession()`)
- 증거: T07·T08(403, `WWW-Authenticate` 없음), T10·T11(401, 로그아웃 처리)

### 1-2. 401 안에서도 원인을 나눈다
| code | 의미 | 증거 |
|---|---|---|
| `TOKEN_REQUIRED` | 헤더가 없거나 `Bearer <토큰>` 형식이 아님 (뒤가 빈 `Bearer `도 포함) | T04, T11 |
| `INVALID_TOKEN` | 토큰처럼 생겼지만 서명·클레임이 틀림, 또는 없는 사용자 | T09 |
| `TOKEN_EXPIRED` | 서명은 정상인데 만료 시각이 지남 | T10 |
- 코드: `AuthService.currentUserId()`
- 참고: T09 첫 시도에서 변조 토큰이 빈 값이 되자 `INVALID_TOKEN`이 아니라 `TOKEN_REQUIRED`가 나왔음 → 서버가 "토큰 없음"과 "잘못된 토큰"을 실제로 구분한다는 부수적 증거

### 1-3. 처리 순서: 인증 → 글 존재 → 작성자 권한 → 입력 검증 → DB 변경
- 그래서 Bob이 Alice 글에 공백 제목을 보내면 400이 아니라 **403**, 토큰 없이 없는 글을 수정하면 404가 아니라 **401**
- 이 순서는 제공 코드 `BoardController.update()/delete()`에 이미 있었고, 학생 구현은 그 안에서 호출되는 `currentUserId`와 `assertOwner`
- 증거: T07(정상 토큰이라 403), T14·T17에서 추가 확인 예정

## 2. 화면 제어와 서버 검사의 구분

### 2-1. 버튼 숨김은 편의 기능, 실제 차단은 서버
- `canEdit()`가 false면 수정·삭제 버튼을 안 보여 줄 뿐, 누군가 curl로 직접 요청하면 화면은 아무것도 막지 못함
- 실제로 막는 것은 서버의 `AuthService.assertOwner()` (DB에 저장된 authorId와 검증된 사용자 ID 비교)
- 증거: T07 화면(버튼 없음) + T07·T08 curl(403, 원문 그대로)

### 2-2. 작성자는 요청 본문이 아니라 토큰에서 정한다
- 글 등록 요청 본문에는 title·content만 있고, 서버가 `currentUserId()`로 검증한 ID를 authorId로 저장
- 본문에 authorId·userId를 넣으면 400으로 거부 (작성자 위조 방지)
- 증거: T05(본문에 작성자 없음 → authorId 1), T12에서 위조 시도 확인 예정

## 3. 상태 유지의 구분

### 3-1. 게시글 유지(DB)와 로그인 유지(메모리)는 다르다
- 게시글은 SQLite 파일(`backend/data/board.sqlite`)에 저장 → 새로고침·서버 재시작 후에도 남음
- 로그인 토큰은 브라우저 탭의 JavaScript 메모리 변수(`api.js`의 `session`)에만 있음 → 새로고침하면 사라짐 (과제 요구사항이며 정상)
- 증거: T15(서버 재시작), T16(새로고침) 예정. 참고로 2026-10-26에 만든 글이 PC를 껐다 켠 10-27에도 남아 있었음

### 3-2. 왜 localStorage에 토큰을 두지 않는가
- localStorage·sessionStorage는 페이지의 아무 스크립트나 읽을 수 있어서, XSS 취약점이 생기면 토큰을 통째로 빼 갈 수 있음
- 메모리 보관은 그 위험을 줄이는 대신 새로고침 시 로그인이 풀리는 불편을 감수
- 코드: `api.js` 상단 `let session = {...}` (storage API 호출 없음)

### 3-3. 로그아웃 ≠ 서버에서 토큰 무효화
- 로그아웃은 이 탭의 메모리에서 토큰을 지울 뿐, 서버는 토큰 목록을 저장하지 않으므로(stateless JWT) 이미 복사된 토큰은 만료(exp) 전까지 계속 유효함
- 그래서 TTL을 짧게(기본 90초) 두는 것이 피해 범위를 줄이는 방법
- 증거: T11은 "로그아웃 후 프론트가 토큰을 보내지 않음"을 확인한 것이지, "서버가 그 토큰을 거부함"을 확인한 것이 아님

## 4. JWT 검증 관련

### 4-1. decode와 verify는 다르다
- JWT 앞 두 부분은 Base64로 인코딩만 되어 있어서 누구나 읽을 수 있음(decode). 서명을 키로 검증해야 내용이 위조되지 않았음을 믿을 수 있음(verify)
- 코드: `AuthService` 생성자의 `Jwts.parser().verifyWith(key).requireIssuer(...).requireAudience(...)`와 `parseSignedClaims()`
- 증거: T09(서명 한 글자만 바꿔도 401)

### 4-2. 라이브러리가 다 해 주지 않는 것은 직접 검사
- JJWT는 `exp`가 아예 없는 토큰도 통과시키므로 `claims.getExpiration() == null`을 직접 확인
- 허용 알고리즘을 HS256으로 고정하는 검사, sub 형식(양의 정수 문자열)과 실제 계정 존재 확인도 직접 추가
- 증거: `ai-usage-log.md`의 조작 토큰 15종 검사(HS512, alg=none, iss/aud 불일치, exp·sub 누락, 없는 사용자 등)

### 4-3. 로그인 실패 응답을 하나로 통일
- 없는 이메일과 틀린 비밀번호 모두 401 `INVALID_CREDENTIALS`, 같은 메시지
- 응답이 다르면 어떤 이메일이 가입되어 있는지 알아낼 수 있기 때문 (제공 `Users.verify()`는 없는 계정도 해시 계산을 해서 응답 시간 차이도 줄임)
- 증거: T03

### 4-4. 서버 키는 시작할 때 검사
- `JWT_SECRET`이 비었거나, 제공 예시 키이거나, 64자리 16진수가 아니면 `AuthService` 생성자에서 예외 → 서버가 아예 뜨지 않음
- 잘못된 키로 운영되다가 나중에 발견되는 것보다 시작 시점에 막는 편이 안전
- 증거: `ai-usage-log.md` 2026-10-26 ② (예시 키, `abc123`으로 기동 거부)
